# Offline Emergency Civic Information Card with Verified Local Contacts

Issue: [#761](https://github.com/Shubham-raj-singh/Civic-Help-Setu/issues/761)

Route: `/offline-emergency-card` (aliases: `/emergency-card`, `/services/offline-emergency-card`)

The Offline Emergency Civic Information Card gives residents a small, printable
and installable set of emergency and civic helplines that keeps working when the
network does not. Every public number must be linked to an official government
source and to the date a human last checked it. Numbers are never generated by
AI, and no contact becomes public without a reviewer decision.

This build is local-first: the browser stores one versioned JSON bundle in
`localStorage` and falls back to memory when storage is unavailable. The service
layer is the trusted boundary. Shared production deployments must repeat the
same role, jurisdiction, validation and state-transition checks on a server.

## User-facing workflow

1. **Open the public card.** The card lists approved contacts for the selected
   jurisdiction plus national helplines. Search by service, organisation,
   number, address or language; filter by category and freshness; switch to a
   table view for screen readers and narrow screens.
2. **Read the proof.** Each contact shows the official source title, a link to
   the government page, the last verification date and a text freshness label:
   `Recently verified`, `Review due soon` or `Outdated — verify before relying
   on it`.
3. **Install the card.** Installation saves the selected contacts, a personal
   note and display preferences on the device. It works offline. The same
   action is idempotent, so retrying a request does not create duplicates.
4. **Use it offline.** Offline search and open work from the saved snapshot.
   Refresh uses the last approved copy already on the device and records an
   `offlineRefresh` sync event. It never implies that a new online approval has
   arrived.
5. **Delete local data.** Deleting the card removes the saved contacts, note,
   preferences and snapshot immediately. Exported files never contain internal
   contact IDs, actor identities, audit data or idempotency keys.
6. **Staff review.** Operators create drafts and submit them. Reviewers check
   the official source, record the verification method and date, and publish,
   return or archive the contact. Every override requires a written reason.

## Roles and capabilities

Roles are resolved by `src/services/offlineEmergencyCardAccessControl.js`.
`getCurrentActor()` supplies the authenticated actor; the workspace role
selector is a local demonstration control and is not a production authority.

| Capability | Public | Citizen | Operator | Reviewer | Administrator |
| --- | --- | --- | --- | --- | --- |
| View the public card and search | Yes | Yes | Yes | Yes | Yes |
| Install, refresh, export and delete own local card | No | Yes | Yes | Yes | Yes |
| Read own installed card and preferences | No | Yes | Yes | Yes | Yes |
| Create/edit/submit contacts in assigned jurisdiction | No | No | Yes | No | Yes |
| Publish, return or archive contacts | No | No | No | Yes | Yes |
| Restore an archived contact as a draft | No | No | No | No | Yes |
| Read the audit trail | No | No | No | Yes | Yes |
| Generate/decide review recommendations | No | No | No | Yes | Yes |
| Run retention, rollback, restore or reset | No | No | No | No | Yes |

Jurisdiction scoping is enforced on every staff read and write. An actor with
`jurisdictionId: 'LKO'` cannot read or edit a `NATIONAL` contact. An
administrator with no jurisdiction assignment has all-jurisdiction scope; an
administrator with an assignment is limited to it. Public reads are not
jurisdiction-authenticated, but they only expose published projections.

## Data model

One bundle (`civic_offline_emergency_card_v1`) contains the collections below.
The backup key is `civic_offline_emergency_card_v1_backup`.

| Collection | Purpose |
| --- | --- |
| `contactSources` | Official portals, gazettes, directories, helpline pages and district sites. Stores publisher, URL, retrieval date, status and reason history. |
| `jurisdictionContacts` | Working contact records with status, category, jurisdiction, source link, verification metadata, version and review interval. |
| `contactVersions` | Append-only snapshots. The newest published version is the public projection, so a pending revision never changes the live card. |
| `offlineCardPreferences` | Device-local selection, note, `includeNational`, `largeText` and `showTable` flags, owner and version. |
| `syncEvents` | Install, refresh, preference, export, delete, offline-open and no-change events, with idempotency keys and contact counts. |
| `recommendations` | Deterministic, versioned review suggestions with inputs, reasons, feature window, ruleset version, priority and human decision. |
| `auditEvents` | Append-only staff events: create, update, submit, publish, changes requested, archive, restore, source archive, recommendation decisions, retention, rollback and reset. |

The UI-facing entities are `EmergencyContact`, `ContactSource`,
`OfflineCardPreference` and `SyncEvent`.

### Contact state machine

| From | Allowed to |
| --- | --- |
| `draft` | `pending_review`, `archived` |
| `pending_review` | `published`, `changes_requested`, `archived` |
| `changes_requested` | `pending_review`, `archived` |
| `published` | `pending_review` (new revision), `archived` |
| `archived` | `draft` (administrator restore only) |

Invalid transitions return `OFFLINE_CARD_INVALID_STATE_TRANSITION`. Editing a
published contact creates a new pending revision; the previous published
version remains public until a reviewer approves the new one. Archiving removes
the contact from the public projection but keeps it for audit and restoration.

### Versions, concurrency and idempotency

- Contact and preference updates require `expectedVersion`. A stale tab receives
  `OFFLINE_CARD_VERSION_CONFLICT` rather than overwriting a newer decision.
- Install, refresh, preference and source writes accept an idempotency key.
  Replaying the same key and payload returns the original result; reusing the
  key with a different payload returns `OFFLINE_CARD_IDEMPOTENCY_CONFLICT`.
- Public references (`publicRef`) are stable hashes derived from the contact ID
  and category. Internal IDs, actor IDs and idempotency keys are omitted from
  public and exported projections.

### Freshness

`freshnessFor(contact, now)` compares the last verification date with the review
interval:

- `fresh` — within the review interval.
- `review_due` — inside the final 30 days before the next review.
- `stale` — past the review date. The contact remains visible with an explicit
  warning and the official source to re-check.

Published contacts are never silently removed because they are old. The seeded
Lucknow fire contact is deliberately old so the stale path is exercised in
tests and demos.

## Deterministic review recommendations

Recommendations use ruleset `emergency-card-review-rules-2026.1` and a 365-day
feature window. They are explainable and never mutate a contact automatically.
Each recommendation records:

- rule ID and label;
- contact, jurisdiction and category inputs;
- the reason and priority;
- `rulesetVersion`, `featureWindow`, `executedAt`;
- `requiresHumanDecision: true`;
- version and status for optimistic concurrency.

Rules include overdue verification, stale official source, missing critical
category and similar deterministic checks. A reviewer can accept, edit or reject
with a reason. Accepted recommendations are advisory; the reviewer still uses
the normal contact workflow to change and publish a contact.

## Persistence, migrations and indexes

- Schema version: `1`.
- Storage key: `civic_offline_emergency_card_v1`.
- Backup key: `civic_offline_emergency_card_v1_backup`.
- Every write runs in `runOfflineCardTransaction`: the mutator works on a deep
  clone and the bundle is persisted only after it returns. A thrown mutator
  leaves the previous bundle intact and reports
  `OFFLINE_CARD_MIGRATION_FAILED`.
- Missing storage is seeded from the verified seed bundle. `seed: false`
  creates an empty store.
- Corrupt JSON falls back to a seeded store and marks
  `meta.recoveredFromCorrupt`.
- Legacy bundles are migrated once and the history entry is written to
  `meta.migrationHistory`. Legacy contacts are forced to `draft`, have no
  verification date and receive an archived placeholder source when no official
  source exists. They can never become public through migration alone.
- Storage failures (quota, private browsing, disabled storage) keep the data in
  memory for the visit and return `storage.persisted: false` plus a warning.
  The UI shows a low-storage banner instead of pretending the card is durable.

Indexes are rebuilt in memory after each transaction:

- `sourcesById`, `contactsById`
- `versionsByContact`, `publishedVersionByContact`
- `contactsByJurisdiction`, `contactsByStatus`, `contactsByCategory`
- `sourcesByJurisdiction`
- `preferencesByOwner`, `syncEventsByOwner`
- `recommendationsByContact`, `recommendationsByStatus`
- `auditByEntity`, `auditByJurisdiction`

These indexes keep search, public projection, staff lists and audit reads
predictable without a database.

## Retention

The administrator retention action is idempotent and appends a
`retention.applied` audit event with counts.

| Data | Retention |
| --- | --- |
| Sync events | 180 days |
| Inactive device preferences | 365 days |
| Audit events | 730 days |
| Archived contacts and their versions/recommendations | 1095 days after archival |
| Published contacts | Indefinite; stale records stay visible with warnings |
| Personal notes | Device-local; removed immediately when the card is deleted |

## Rollback, restore and reset

- **Rollback** copies the current bundle to the backup key, then restores the
  verified seed. The current state is recoverable until another rollback or
  backup restore overwrites the backup.
- **Restore backup** loads the backup bundle and appends a
  `migration.backup_restored` audit event.
- **Reset to empty** removes all sources, contacts, versions, preferences,
  recommendations and sync events, then appends a `card_store.reset` audit
  event. Use it only for a documented reset.

All three actions require the `migration.run` capability (administrator) and a
reason where the UI asks for one.

## Environment and configuration

This feature needs no environment variables, API keys or external service. It
uses the same Vite/React application, `localStorage` and the existing network
context. Relevant flags:

- `isOnline` from `NetworkContext` changes offline messaging and refresh
  behaviour; it never fabricates new approvals.
- The role and jurisdiction selectors in the workspace are demonstration
  controls. Production must derive both from the authenticated session and
  enforce them server-side.
- The service can be exercised in tests by passing a storage object and a fixed
  `now` timestamp; no browser is required.

HTTPS government page and every contact links to one source. National examples

### Updating a contact

1. Create or select an active official source in the same jurisdiction.
2. Create/edit a draft. Use only the number and service details shown on the
   official page. Do not infer, generate or complete a missing number.
3. Submit the draft for review.
4. As a reviewer, open the official URL, record how it was checked and the
   verification date, then publish or return it with a reason.
5. If the source has moved, archive the old source with a reason after moving
   published contacts to the new source.

## Manual fallback

If the browser cannot store data, the card remains usable for the current visit
but is not durable. The UI tells the user this. For a reliable paper fallback:

1. Export the card as JSON or print the public/installed view.
2. Keep a printed copy with the date and the official source links.
3. Dial **112** for police, fire or ambulance emergencies when the local number
   is uncertain. Do not rely on an outdated contact without checking the linked
   official source.
4. Report a wrong or outdated number through the staff review workflow or the
   platform issue tracker; do not edit the number locally and assume it is
   official.

## Privacy and security

- No Aadhaar numbers, PANs, personal phone numbers, personal email addresses,
  medical records, credentials, OTPs or uploaded documents are accepted in
  free text. The validation layer detects and rejects them.
- Public projections expose only approved fields, a stable public reference and
  the official source URL. They omit internal IDs, owner/actor identities,
  notes, audit events, idempotency keys and sync events.
- Search input is length-limited and sanitised. Markup-only input returns no
  results instead of falling back to the full list.
- Staff actions are capability-checked and jurisdiction-checked in the service,
  not only hidden in the UI. Invalid state transitions and stale versions are
  rejected.
- Audit events are append-only in the service model. Overrides require a reason
  where the workflow demands one.
- The seed contains only public office contacts and official sources; it
  contains no resident data.

## Accessibility and UI states

The workspace is keyboard operable and uses native headings, labels, tables,
`aria-live` announcements, tab semantics and text status labels. Colour is never
the only signal. It includes:

- loading skeleton;
- empty public card and empty staff queues;
- offline banner with last refresh time;
- stale contact warnings with the source to re-check;
- permission-denied and unauthenticated states;
- recoverable error state with retry;
- low-storage / memory-only warning;
- table view for contact lists.

## Known limitations

- This repository is a frontend-only demonstration. `localStorage` is not a
  shared source of truth and browser-side role checks are not a security
  boundary for a real multi-user deployment.
- There is no automatic verification of an official page. A human reviewer must
  check the source and record the verification date.
- The seed is illustrative and limited to national helplines plus Lucknow. Add
  other jurisdictions through the same source/contact/review workflow.
